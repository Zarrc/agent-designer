# 好 / 坏范例对照

每条都标注**为什么**好或坏 —— 照着抄形状，别抄内容。

---

## 1. `description`（路由信号）

### ✅ 好：三段式，有触发语、有能力、有边界

```yaml
description: 简历优化专员。当用户要「记一条工作成果 / 把这周做的事记进简历素材」「按这个 JD 定制简历」「体检简历缺什么」时使用 —— 从零散工作记录提炼量化成果、按目标岗位重排改写简历、标出量化数字缺口。它读写简历真源目录下的真源与派生物；面向用户的最终汇报由主代理完成。
```

**好在**：① 触发语是用户真会说的话；② 能力用破折号连成一串，一眼看清；③ 边界两句写死（写区 + 汇报权归谁）。

### ❌ 坏：抽象情境，无从路由

```yaml
description: Helps with resume-related tasks when the user needs assistance.
```

**坏在**：没有任何具体触发语；「needs assistance」等于没说。用户说「帮我记条成果」时，这句命中不了。

### ❌ 坏：只写能力，不写边界

```yaml
description: 简历优化专家，可以改写简历、生成求职信、做职业咨询、分析岗位、模拟面试。
```

**坏在**：职责过载（5 件事），且没写它**不做什么** —— 会和「职业规划」「面试准备」等其它 agent 抢路由。

## 2. `tools` 与边界的一致性 ⭐ 最常翻车

### ❌ 坏：声称只读，却拿着写权限

```yaml
description: 它只读 vault 各档案，不写简历。
tools: Read, Glob, Grep, Write, Edit, Bash, WebSearch, WebFetch
```

**坏在**：`description` 承诺「只读、不写」，`tools` 里却有 `Write, Edit`。
**自然语言护栏 harness 不强制** —— 它想写就能写。正确做法二选一：

```yaml
# 方案 A：把权限收窄，让描述成为事实
tools: Read, Glob, Grep, WebSearch, WebFetch

# 方案 B：确实需要写，就改描述，别撒谎
```

### ✅ 好：最小白名单 + 与描述对齐

```yaml
description: ……它只写 `.claude/agents/` 与 `.claude/skills/`，不改 CLAUDE.md。
tools: Read, Write, Edit, Glob, Grep, Bash, WebSearch, WebFetch
```

**好在**：需要写（要产出定义文件）、需要 Bash（要跑 `claude plugin validate`）、需要联网（要做调研）—— 每个工具都能在正文里指出用途。

> 判断口诀：**逐个工具问「正文哪一步用到它？」** 答不上来的就删。

## 3. 锚点

### ❌ 坏：标题塞进引用块

```markdown
> ### 📍 路径锚点（子代理依赖 · 搬目录前必读）
```

**坏在**：它**不是** Markdown 标题，是引用块里的一行文字。`[[CLAUDE.md#路径锚点]]` **永远**指不到 —— 而且不会报错，只会在点击时静默失败。文件里看着像有这一节，链接却是死的。

### ✅ 好：真标题

```markdown
## 📍 路径锚点
```

## 4. 护栏写法

### ❌ 坏：靠暗示

```markdown
- 注意不要编造数据。
- 尽量保持准确性。
```

**坏在**：「注意」「尽量」是软语气，模型容易自我开脱。

### ✅ 好：显式否定 + 可判定后果

```markdown
## 🚨 硬性护栏

1. **不许编造** —— 库名、URL、字段名、文件路径。不确定就标「未核实」，或去核实。
2. **不许跳过准入闸门。** 用户说「建」不等于免检。
3. **同错 3 次 → 停下来报告**，不静默重试。
```

**好在**：每条都是否定句 + 明确的替代动作（「标未核实」「去核实」「停下来报告」），不是「请小心」。

## 5. 职责粒度

### ❌ 坏：一锅烩

```
一个 agent 同时负责：知识库摄取 / 认证备考 / lint 检查 / 收件箱清理 / 写日报
```

**坏在**：4-5 块互不相关的职责 → `description` 没法写清楚 → 路由打架 → 正文必然膨胀。
拆成多个 agent，或把其中真正可复用的部分做成 Skill。

### ✅ 好：只留两个理由

```
需要独立评判 → 拆
需要隔离上下文 → 拆
只是「东西多」→ 不拆，那说明该拆的是 Skill / 文档结构
```
